# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A multi-user, cloud-deployed prescription knowledge base with OCR and AI chat. Parents create an account, store their child's prescription records, and ask natural-language questions over them — scoped per user. It summarizes saved records only; it does not give medical advice.

[Prescription_Assistant_Implementation_Guide.html](Prescription_Assistant_Implementation_Guide.html) is the from-scratch tutorial this codebase was originally built from. Its "Part 1" appendices describe the original single-user/Ollama/ChromaDB/flat-file design; that design has been fully replaced (see below). Its "Part 2 · Multi-User Production" is the design this codebase now actually implements — Postgres, OpenAI, JWT cookie auth, object storage, an Arq worker, Render + Cloudflare. Treat the guide as the historical design doc the migration followed, not as something still being kept in sync with the code — the code has diverged in specifics (see module list below for what's actually there).

## Commands

Everything runs through Docker Compose; there is no requirement to have Node or Python installed on the host. Ollama is no longer part of this stack.

```powershell
# Start everything (Postgres/pgvector, Redis, MinIO, backend, worker, frontend, adminer)
# Requires OPENAI_API_KEY in the environment or a backend/.env file
docker compose up --build

# Rebuild a single service after changing its source
docker compose build backend
docker compose build worker
docker compose build frontend

# Tail logs / diagnose a crashed container
docker compose logs backend
docker compose logs worker

# Bypass the default uvicorn CMD to run a one-off command in the backend image
docker compose run --rm backend python -c "..."

# Stop (Postgres/MinIO data persists in named volumes; ./data is only a
# read-only mount for the legacy JSON import script, see repository below)
docker compose down
```

Frontend-only commands (if working inside `frontend/` with Node installed locally):
```bash
npm run dev       # vite dev server
npm run build      # tsc -b && vite build
npm run preview
```

There is no test suite and no lint config in this repo currently — don't assume `npm test`/`pytest`/`ruff` exist.

Once running via Docker Compose: app UI at `http://localhost:3000`, Swagger UI for backend routes at `http://localhost:8000/docs`, MinIO console at `http://localhost:9001`, Adminer (Postgres UI) at `http://localhost:8080`. Production frontend is deployed separately to Cloudflare (`wrangler.jsonc`) at a split origin from the API — see "Frontend" below.

## Architecture

```
Browser (React SPA -- Cloudflare Pages/Workers in prod, nginx container locally)
   |  HTTP requests, JWT in HttpOnly cookie (split-origin -> SameSite=none+Secure)
   v
FastAPI backend (Render web service in prod / :8000 in Docker Compose)
   |
   +--[POST /api/ocr]------> put_object() -> S3/R2/MinIO, enqueue Arq job, return job_id
   |                            |
   |                            v (async, separate process)
   |                          worker.py: Tesseract OCR -> extraction.py -> OpenAI chat
   |                            |                                            (json_mode)
   |                            v
   |                          ProcessingJob row updated (status/raw_text/extracted)
   |                          frontend polls GET /api/jobs/{id}
   |
   +--[repositories/*]-----> Postgres (async SQLAlchemy), every table scoped by user_id
   |
   +--[services/rag.py]----> hybrid retrieval: pgvector cosine_distance + Postgres
   |                          full-text (tsvector/GIN), merged by reciprocal rank fusion
   +--[POST /api/chat]-----> OpenAI chat completion (json_mode), answers strictly from
                              the retrieved records for that user
```

**No Ollama, no ChromaDB, no flat JSON file anymore.** OCR still runs via Tesseract, but only inside the Arq worker (`worker.py`), never inline in a request — uploads return a `job_id` immediately and the frontend polls `GET /api/jobs/{id}` (`routers/jobs.py`) until it's `done`/`error`.

### Backend (`backend/app/`)

FastAPI app (`main.py`) with routers/repositories/services split by concern:

- `models_db.py` — SQLAlchemy models: `User`, `Child`, `Prescription` (has both `embedding` (`pgvector`) and a `search_vector` `TSVECTOR` column generated by Postgres itself via `Computed(...)`, plus `image_keys` — the object-storage key(s) of the original photo(s), in page order, carried forward from the `ProcessingJob` that produced it), `ProcessingJob` (also `image_keys` — one job can OCR multiple pages into one merged extraction — and `saved`, whether the job's extraction was ever turned into a `Prescription`), `AccountLink`/`AccountInvite` (shared-account access — see "Shared accounts" below). Every user-owned row still carries `user_id`; which user's rows a request actually operates on is resolved separately (see `get_data_owner_id`).
- `schemas.py` — Pydantic request/response models for the routers.
- `db.py` — async SQLAlchemy engine/session; `get_db()` FastAPI dependency.
- `auth/security.py`, `auth/deps.py` — bcrypt password hashing (with a `field_validator`-enforced complexity rule on register/change-password: upper+lower+digit+symbol, min length 10 — deliberately *not* applied to login, since that verifies an existing credential rather than setting one, and would lock out any password that predates the rule), JWT access+refresh token creation/decoding, `get_current_user()` dependency (reads the `access_token` HttpOnly cookie first, falls back to a `Bearer` header for API clients — though nothing currently issues a bearer token to hand to such a client, see below). `token_issued_before_password_change()` rejects a token whose `iat` predates the user's `password_changed_at`, so changing your password invalidates every session/refresh token issued before that point, not just the one making the change. Compares at second granularity on purpose — JWT `iat` truncates to whole seconds on encode while Postgres keeps microseconds, so naive full-precision comparison intermittently rejected a token issued in the very same second as the password change (e.g. the login right after changing it). `get_data_owner_id()` is the other identity dependency: it resolves *whose* data (children, prescriptions, chat, uploads) the logged-in user should act against — their own `user.id`, or the owner they've been granted shared access to as a member (see "Shared accounts"). Every data router uses this instead of `user.id`; identity-only operations (profile, password, account deletion) still use `user.id` directly.
- `services/rate_limit.py` — Redis-backed fixed-window request limiter (`ip_rate_limit`/`user_rate_limit` dependency factories), shared across API instances since it lives in Redis rather than process memory. Fails open (allows the request) if Redis itself is unreachable, so a limiter outage doesn't take the API down. Applied to `/api/auth/{register,login,refresh}` (per-IP, since there's no user identity yet), and per-user to `/api/account/change-password`, `/api/chat`, `/api/ocr`.
- `routers/` — `auth.py`, `account.py`, `children.py`, `prescriptions.py`, `medications.py`, `chat.py`, `ocr.py`, `jobs.py`, `household.py`. Every data route is gated behind `get_current_user` and scoped via `get_data_owner_id`/`repositories/`. `register`/`login`/`refresh` set the auth cookies and return only `{"ok": true}` — access/refresh tokens are never echoed into the JSON body, since anything that can read a response (XSS, over-broad logging) would otherwise get a script-readable copy of a credential the HttpOnly cookie was specifically meant to keep out of reach. `register` also folds a duplicate-email failure into the same generic error text login uses for a bad password (plus a throwaway `hash_password()` call on that branch to keep the timing close to the real signup path), so probing the endpoint can't be used to enumerate registered emails. `children.py` has full CRUD (list/get/create/update/delete). Every `Prescription` must belong to a child: `PrescriptionCreate.child_id` (used by both `POST` and `PUT`, since editing reuses the same schema) is a required `UUID`, not `Optional`, and the router checks it via `repositories/children.py::get_for_user` before accepting it — a Pydantic UUID alone doesn't confirm the id is actually one of the caller's own children, and with deletion now cascading (see below) that ownership check is what stops a request from attaching a record to, or indirectly threatening, a child it has no access to. Deleting a child (`DELETE /api/children/{id}`) cascades to every prescription assigned to them, via the DB's `ON DELETE CASCADE` on `Prescription.child_id` — a deliberate reversal of the original "orphan, don't delete" design from when the column was still optional (see migration `0007_child_delete_cascades`). Getting this right needs `passive_deletes=True` on `Child.prescriptions` in `models_db.py`, not just `ondelete="CASCADE"` on the FK: without it, SQLAlchemy's own unit-of-work nulls the FK on any loaded prescriptions before issuing the `DELETE`, so the DB constraint never actually fires — this looks correct by reading the FK declaration alone and was only caught by testing an actual delete against a running stack. Existing pre-feature rows with a `NULL child_id` are left alone (nothing backfills them); the frontend enforces the same "must pick a child" rule client-side and shows an inline "add a child" prompt in `PrescriptionForm` when the account has none yet, so the requirement doesn't strand a new user with no way to satisfy it. `prescriptions.py` gained `PUT` support in the frontend (editing a saved record reuses the same review form as upload) and `GET /{id}/photos` (presigned URLs for the original image(s)); `ocr.py` accepts multiple files per request (`files: list[UploadFile]`, capped at `MAX_PAGES`) so a multi-page prescription becomes one job instead of several disconnected records; `jobs.py` gained `GET /api/jobs` (list, newest first) so an OCR'd-but-never-saved upload isn't lost the moment the tab closes.
- `repositories/` — plain async-SQLAlchemy query functions per table (`users.py`, `children.py`, `prescriptions.py`, `jobs.py`, `account_links.py`, `account_invites.py`); no ORM-session logic lives in routers.
- `services/objects.py` — thin `boto3` S3-client wrapper (`put_object`/`get_object`/`ensure_bucket`/`delete_prefix`/`presigned_url`) pointed at whatever `STORAGE_ENDPOINT` is configured — MinIO locally, Cloudflare R2 in prod. `delete_prefix()` bulk-deletes everything under an account's `uploads/{owner_id}/` folder; `routers/account.py::delete_account` calls it after the DB delete so uploaded prescription photos don't outlive the account — Postgres FK cascades clean up the rows (`prescriptions`, `children`, `processing_jobs`, `account_links`, `account_invites` all have `ON DELETE CASCADE` to `users`), but nothing else ever touched the underlying files in object storage. `presigned_url()` backs both the record-detail photo viewer and `SourceOut.thumbnail_url` in chat source cards (previously always `None` — nothing linked a saved record back to the photo that produced it until `image_keys` existed).
- `services/ocr.py` — `extract_text_from_image()`, a `pytesseract` wrapper. Only ever called from `worker.py`, never from a request handler.
- `services/extraction.py` — turns raw OCR text into structured prescription fields by prompting OpenAI chat (`json_mode=True`) via `services/llm.py`. Falls back to `_fallback_extract()`, a regex-based best-effort parser, if the call fails or returns unparseable JSON. Always returns a dict, never raises to the caller.
- `services/embeddings.py` — `embed_text()`, one call to OpenAI's embeddings API (`openai_embed_model`).
- `services/llm.py` / `services/openai_client.py` — shared OpenAI async client + `chat_completion()` helper (temperature, `json_mode`), used by both `extraction.py` and `rag.py`.
- `services/budget.py` — a process-wide `TokenBudget` that estimates a request's token cost up front and rejects it before calling OpenAI if it would exceed `max_tokens_per_request`; `record()` logs actual usage OpenAI reports back, exposed via `GET /api/metrics`.
- `services/rag.py` — `answer()`: embeds the question (degrades to full-text-only retrieval if the embed call fails), calls `repositories/prescriptions.py::search_for_user()` for hybrid pgvector + full-text retrieval (see docstring there for the reciprocal-rank-fusion rationale), then asks OpenAI to answer strictly from the retrieved records, classifying each part of the answer as record-grounded vs. general knowledge (see prompt framing below).
- `worker.py` (run via `Dockerfile.worker`, Arq over Redis, config in `queue.py`) — the single job type `process_ocr_job`: fetch the uploaded image from object storage, OCR it, run extraction, write the result onto the `ProcessingJob` row.
- `metrics.py` — in-process request volume/latency/error-rate counters, exposed alongside token usage via `GET /api/metrics` (login-gated, not public).

**Index consistency**: there is no separate rebuild-the-index step anymore — `embedding` and `search_vector` live as columns on the `Prescription` row itself (the latter Postgres-generated), written/updated in the same transaction as the row via `repositories/prescriptions.py`. Nothing can drift out of sync the way a separate ChromaDB collection could.

**Both OpenAI-calling code paths degrade gracefully**: `extraction.py` falls back to regex extraction; `rag.answer()` falls back to full-text-only retrieval if embedding fails, and to a "records found but LLM unavailable" message with raw context if the chat call itself fails. Neither raises an unhandled exception when OpenAI is unreachable or `OPENAI_API_KEY` is unset — preserve this pattern if you touch either.

**System prompt framing** (`rag.py`): the chat system prompt deliberately frames answers as *reporting already-recorded history* rather than *giving medical advice* — this was tuned to stop the model from refusing to state a dosage/duration that's already written in a saved record. Keep this framing if you edit the prompt; a more clinical-sounding prompt tends to reintroduce refusals.

The prompt also classifies each question into one of three types — record-specific fact, general education, or judgment/safety — each with its own answering rule, plus a conflict rule (records win over general knowledge; a discrepancy must be flagged, never silently resolved) and a compound-question rule (a question can mix types — e.g. "what dose was X prescribed at, and what does X treat" — answer every part per its own rule, never drop the general half just because the record half comes back "not found"). The model marks which part of its answer came from where using `[[record]]`/`[[general]]` **markers**, not a required open/close pair — deliberately lenient, because in practice the model doesn't reliably close tags (observed: reusing `[[general]]` itself as the "close," or dropping the marker for one sentence in a mixed answer). Whatever follows a marker is that type until the next marker or end of string; `AskView.tsx`'s `parseSourceSegments` reflects this (a marker regex + running "current type," not a paired-tag match) and must stay lenient if you touch it. "Records don't contain this" statements are deliberately left with no marker at all — they're not drawn from either source, and marking them `[[record]]` was causing the UI to show facts/sources pulled from an unrelated retrieved-by-fuzzy-search record next to a "not found" answer.

That last point matters beyond styling: `ChatResponse.grounded` (`rag.py`) is `True` only when `text` actually contains a `[[record]]` marker, and `med`/`facts`/`safety_note`/`sources` are only populated when `grounded` is true — retrieval is fuzzy (vector + full-text) and always returns its top-k best-available hits even when none are relevant, so "a hit came back" is never sufficient justification to show record-derived UI chrome next to an answer that didn't actually use it. The frontend shows a small "not based on your saved records" pill (`.grounding-note`) whenever `grounded` is false, instead of counting on the model's prose to communicate that reliably.

Settings (`config.py`) are a `pydantic_settings.BaseSettings` reading from env vars / `.env`: `database_url` (Postgres, normalised to the `asyncpg` driver via `async_database_url`), `redis_url`, `openai_api_key`/`openai_chat_model`/`openai_embed_model`/`embedding_dim`, `jwt_secret`/`jwt_alg`/`access_ttl_min`/`refresh_ttl_days`, `storage_endpoint`/`storage_region`/`storage_bucket`/`storage_access_key`/`storage_secret_key` (S3-compatible: MinIO locally, R2 in prod), `cors_origins`, `max_upload_mb`, `rag_top_k`, `max_tokens_per_request`, `fulltext_language`, `enforce_https`/`hsts_max_age`/`trusted_hosts` (off by default so local HTTP dev works), and `cookie_secure`/`cookie_samesite`/`cookie_domain`. In Docker Compose these are set directly in `docker-compose.yml` per service; in production they're set in `render.yaml` (`sync: false` entries are filled in via the Render dashboard, not committed).

`jwt_secret` has **no default** — `Settings()` raises at startup if it's unset, on purpose. A hardcoded fallback here would mean any deployment that forgot to set the env var would silently sign every session with a secret an attacker could read straight out of the public repo, letting them forge a valid token for any user. `docker-compose.yml` and `render.yaml` both set it for the `worker` service too, even though the worker never signs/verifies a token itself — it imports the same `Settings` object as the API, so a missing value crashes worker startup, not just the API's.

**Shared accounts** (`routers/household.py`, `repositories/account_links.py`, `repositories/account_invites.py`): full symmetric access, no owner/viewer role split, deliberately — the model is "one household's data pool," not a permissions system. `AccountLink` is a single join row per member (`member_user_id` is unique — a user can be a member of at most one shared account, and a member can't themselves invite further members, no nested sharing). Invites are link/code-based (`AccountInvite.token`, 7-day expiry, single-use), not email-based, since no email-sending infrastructure exists in this codebase — the owner generates a link in `ProfileModal` and sends it themselves through whatever channel they like; the invitee redeems it at `/join/:token` while logged into their own account. Once linked, every data router resolves `get_data_owner_id()` instead of using `user.id`: a member's data operations (children, prescriptions, chat, uploads) transparently act on the owner's pool, while their own login/session/password stay entirely their own. A member's *pre-existing* records (if any) aren't merged in and aren't deleted — they simply become unreachable through the API while the membership is active, and reappear exactly as before if the member leaves. An owner can't delete their account while they still have members (`account.py::delete_account` checks `account_links_repo.has_members()` first) — deleting out from under active members would leave them pointing at a dead owner id, so the API asks the owner to remove members first instead of trying to handle that state. Rate limits (`services/rate_limit.py`) stay keyed on the *authenticated* `user.id`, never the resolved owner id — each login's own request volume is what's bounded, regardless of whose data pool it's currently operating on.

### Frontend (`frontend/src/`)

React 19 + TypeScript app. `App.tsx` still holds most view state (now including `children: Child[]`, lifted alongside `prescriptions`/`meds` and passed down to `UploadView`/`RecordsView`/`ChildrenModal`); `auth/AuthContext.tsx` now wraps it for login/session state, and `api.ts` is a thin fetch wrapper mirroring the backend routes 1:1, sending cookies (`credentials: "include"`) and reading `VITE_API_URL` (via `API_BASE` at the top of `api.ts`) so the SPA can be built to call a different origin than the one it's served from. Types in `api.ts` should be kept in sync with `backend/app/schemas.py`/`models_db.py` by hand — there's no shared schema/codegen between the two.

`components/PrescriptionForm.tsx` holds the medication/doctor/child/notes form fields shared by both the upload-review flow (`views/UploadView.tsx`) and editing a saved record (`views/RecordsView.tsx`'s `RecordDetail`, which now has an in-place edit mode instead of view-only). `components/ChildrenModal.tsx` is the add/rename/remove UI for `Child` records, opened from a "Manage" row in `ProfileModal.tsx`. `UploadView.tsx` also shows a "pending uploads" list (jobs that finished OCR but were never reviewed/saved — `saved: false` from `GET /api/jobs`) so a closed tab mid-review doesn't silently lose the upload, and its dropzone/file-input accept multiple files for multi-page prescriptions in one submission. `ProfileModal.tsx`'s "Family & sharing" section and `pages/Join.tsx` (route `/join/:token`) are the shared-account UI — see "Shared accounts" above for the underlying model.

Two deployment paths exist side by side:
- **Docker Compose** (`frontend/Dockerfile` + `nginx.conf`): nginx multi-stage build, proxies `/api/*` to the `backend` container and serves the SPA for everything else. Same-origin, so cookies work with `SameSite=lax`.
- **Production** (`wrangler.jsonc`): the built `frontend/dist` is deployed to Cloudflare (Pages/Workers static assets) at `prescription-pal.com`, calling the API at a separate `api.prescription-pal.com` origin via `VITE_API_URL`. This split origin is why `render.yaml` sets `COOKIE_SAMESITE=none` + `COOKIE_SECURE=true` for the API — see the security note below.

### Current scope / known gaps

Multi-user, cloud-deployed by design now — auth, per-user row scoping (`user_id` on every table, resolved per-request to an effective owner id for shared accounts — see "Shared accounts"), Postgres instead of a flat file, async OCR via a worker queue instead of blocking the request. Schema changes go through Alembic (`backend/alembic/`, `backend/alembic.ini`; current migrations: `0001_init` → `0006_household_sharing`). Remaining gaps worth knowing: no automated test suite or lint config (see "Commands") — every change in this codebase so far has been verified by hand against a live Docker Compose stack, which is the reason the JWT `iat`-precision bug and the worker's missing `JWT_SECRET` were each caught only when something was actually run, not before; `backend/app/scripts/import_json.py` is a one-off migration script for pulling records out of the old `prescriptions.json` format, not something exercised regularly; prescription fields are stored as plaintext in Postgres, not column-level encrypted (see security note below for why); metrics (`services/budget.py`, `metrics.py`) are in-process and per-instance, not centralized — fine at current scale (single Render web service), would need a shared store (e.g. Redis) if the API ever runs multiple replicas; uploaded photos (`image_keys`) have no retention/expiry policy and are never deleted except on full account deletion, so storage cost grows unboundedly with usage.

### Production infrastructure

This is the guide's "Part 2 · Multi-User Production" design, actually deployed: Postgres+pgvector and Redis provisioned by `render.yaml` (or swappable for Neon/Upstash via `sync: false` + external URLs), object storage on Cloudflare R2 (`services/objects.py`, S3-compatible), API (`backend/Dockerfile`) and worker (`backend/Dockerfile.worker`) as separate Render services from one repo, frontend on Cloudflare (`wrangler.jsonc`) at the `prescription-pal.com` custom domain talking to `api.prescription-pal.com`.

**Security specifics worth knowing**: cookies use `SameSite=lax` only when frontend and API share an origin (the Docker Compose nginx-proxy setup); the actual production split-origin deployment (SPA on Cloudflare, API on Render) requires `SameSite=none` + `Secure=true`, which is what `render.yaml` sets — get this wrong and auth silently breaks (cookie never sent). Prescription fields are deliberately *not* encrypted at the column level — RAG needs plaintext to embed and to send as LLM context, so encrypting them would break search; the design relies on provider-level encryption at rest (Render Postgres/Upstash/R2) plus TLS everywhere instead. Both `backend/Dockerfile` and `backend/Dockerfile.worker` create and switch to an unprivileged `appuser` before `CMD` — neither the API nor the worker process runs as root inside its container. Login/register/refresh are IP-rate-limited and chat/OCR/change-password are per-user-rate-limited via `services/rate_limit.py`; every free-text request field (`ChatRequest.question`, prescription fields, medication fields, password fields, etc.) carries an explicit `max_length` in `schemas.py` so a single oversized payload can't blow up OpenAI cost or embedding calls.
